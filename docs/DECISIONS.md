# Decisions

Record of every decision taken while building SocialSignal: the decision, the
alternatives considered, why it was chosen and its trade-offs. It feeds
[`DESIGN.md`](../DESIGN.md). These decisions supersede the "Technical starting
point" section of [`CLAUDE.md`](../CLAUDE.md).

> **Review status.** The decisions and the verified facts were agreed in steps
> 0 and 1. The *Options / Why / Trade-off* write-ups were drafted by the AI
> agent in step 2 from those agreed decisions and are pending the author's
> review (tracked in [`PROGRESS.md`](PROGRESS.md)).

Identifiers: **A** = interpretation of the brief, **D** = other design
decisions, **E** = development environment, **R** = repository layout.

## 1. Interpretation of the brief

### A1. Which "small local LLM", and how to serve it

- **Requirement:** a small, local LLM for sentiment analysis, with "Gemma 4
  A2B" as the example; no cloud LLM APIs.
- **Options:**
  - Model: Gemma 4 E2B, Gemma 4 E4B, larger Gemma 4 variants (12B, 26B A4B,
    31B), or a non-LLM classifier (lexicon-based or a fine-tuned encoder).
  - Serving: llama.cpp server, Ollama, vLLM, or the model loaded in-process
    with `transformers`.
- **Decision:** Gemma 4 **E2B**, quantised to GGUF Q4, served by the
  **llama.cpp server** (official multi-arch image). The weights are fetched
  during `make build` and baked into the image; they are never downloaded at
  runtime. Model output is constrained with a JSON schema. **E4B** is the
  fallback if E2B quality is not good enough. *Step 7a: Google's official
  QAT Q4_0 file. E2B scored 14/14 on a small labelled set, so the fallback
  is not needed (D22).*
- **Why:**
  - "Gemma 4 A2B" is not a published variant. The family is E2B, E4B, 12B,
    26B A4B and 31B (verified, see [Verified facts](#5-verified-facts)). E2B
    is the smallest one and matches the "small" intent.
  - llama.cpp runs on CPU on both amd64 and arm64 (the reviewer may be on an
    ARM Mac) and ships an official multi-arch image with an HTTP API.
  - JSON-schema-constrained output guarantees a parseable label instead of
    free text that has to be scraped.
  - Baking the weights into the image means the LLM pod needs no egress at
    all, and the same image can be carried into an air-gapped site.
  - Ollama pulls models at runtime by default and adds a layer we do not
    need; vLLM targets GPUs; in-process `transformers` would put a heavy
    runtime in the worker image.
  - A non-LLM classifier would not meet the brief ("use a small, local LLM").
- **Trade-off:** large image and slower `make build`; Q4 quantisation and a
  small model lose accuracy (sarcasm, irony, mixed posts); CPU inference is
  slow, which is mitigated by classifying each post only once (A9) in batch
  jobs (A8).

### A2. What "recent" means

- **Requirement:** a summary of the recent sentiment of each subscription.
  No window is defined.
- **Options:** a time window only (e.g. last 24 h); a post count only; a
  count capped by a time window; everything since the subscription started.
- **Decision:** the **last 50 posts from the last 7 days**. Both values are
  configurable.
- **Why:** a time window alone is unbounded for busy hashtags, which matters
  with CPU inference; a count alone can include months-old posts for quiet
  handles. The combination bounds the LLM cost and keeps the data recent.
- **Trade-off:** for a very busy hashtag, 50 posts cover only a short span,
  so "recent" means "latest sample". A quiet handle may have few or no items
  in the window, which the item count (requirement 3) makes visible.

### A3. What a "summary of the recent sentiment" contains

- **Requirement:** a summary of the recent sentiment, how many items it
  covers and when it was last updated.
- **Options:** only a dominant label; label plus per-label counts; a
  free-text LLM summary; an average numeric score.
- **Decision:** dominant label (`positive` / `neutral` / `negative`) + count
  per label + one sentence generated by the LLM, plus the number of items and
  `updated_at`. Degraded mode: if the LLM fails, only the label and the counts
  are shown, and the previous `updated_at` is kept, so staleness stays
  visible.
- **Why:** the label and the counts are a deterministic aggregation of the
  per-post classifications: cheap, auditable and robust. The counts show
  nuance (a split of 20/18/12 is not a clear "positive"). The sentence adds
  readability for the analyst.
- **Trade-off:** the sentence costs one extra LLM call per subscription and
  run; three classes lose intensity and "mixed" nuance; ties between labels
  need a rule (decided in step 8).
- **Completed in step 8 (D24), by the author:**
  - **Ties are `neutral`:** whether the tie is negative with neutral,
    positive with neutral, or positive with negative. No posts in the window
    means no label.
  - **`updated_at` is when the summary was generated.** It moves only when
    the summary's posts change, or when its sentence is finally written. It
    does not move on a run that finds nothing new.
  - **The sentence costs one LLM call only when the posts change**, not on
    every run.

### A4. Users and authentication

- **Requirement:** analysts subscribe and unsubscribe. Identity,
  authentication and per-analyst lists are not mentioned.
- **Options:** no authentication with one shared list; per-analyst
  subscriptions with login (e.g. OIDC); basic authentication at the ingress.
- **Decision:** **no users and no login**. One subscription list shared by
  all analysts.
- **Why:** the brief does not require identity, the timebox is one evening,
  and the system is reachable only from the analysts' local network. The
  effort goes to what the brief emphasises: the security boundary, high
  availability and updates.
- **Trade-off:** anyone on the local network can change the subscriptions,
  and there is no per-user audit trail. Listed as an open item.

### A5. Enforcing "local network only" for the analysis application

- **Requirement:** only the ingestion may reach the internet; the analysis
  side may only reach the analysts' local network; the boundary must be
  enforced by the infrastructure.
- **Options:** Kubernetes NetworkPolicies; separate clusters or node pools
  per zone; a firewall or egress proxy outside the cluster; a service mesh or
  L7 policy engine; checks in application code (ruled out by the brief).
- **Decision:** three namespaces (`ingest`, `data`, `analysis`) with
  **default-deny ingress and egress** in all of them, plus minimal allow rules
  per component:

  | Component (namespace) | Ingress allowed from | Egress allowed to |
  |---|---|---|
  | API (`analysis`) | Traefik only | PostgreSQL 5432, DNS |
  | Summary worker (`analysis`) | nothing | PostgreSQL 5432, DNS, LLM |
  | LLM server (`analysis`) | summary worker only | nothing |
  | Ingestor (`ingest`) | nothing | internet on TCP 443 only, excluding private and link-local ranges; PostgreSQL 5432; DNS |
  | PostgreSQL (`data`) | 5432 from the ingestor, the API, the worker and the migration Job | nothing |
  | Migration Job (`data`) | nothing | PostgreSQL 5432, DNS |

  DNS means port 53 TCP/UDP, only towards the CoreDNS pods (`kube-system`,
  `k8s-app=kube-dns`), selected by labels; no IP addresses are hard-coded.
  PostgreSQL is the only bridge between zones.

  **Refinement (step 3c, approved by the author).** The ingestor's internet
  access is limited to TCP 443, and 10/8, 172.16/12, 192.168/16, 100.64/10
  and 169.254/16 are excluded. The ingestor parses untrusted content from
  the internet; if it were compromised, it must not reach the LAN, the
  cluster nodes, the Kubernetes API (`172.18.0.2:6443` here) or cloud
  metadata endpoints.

  `make verify-boundary` proves the rules (D12): the ingestor reaches
  Bluesky and 1.1.1.1 but not the Kubernetes API; the API and the worker
  resolve names but cannot connect out; the LLM cannot even resolve names.
  The PostgreSQL checks are added in step 4 and the LLM checks in step 7.
  It waits a few seconds before testing (see below).
- **Why:** NetworkPolicies are native, declarative and versioned with the
  Helm chart, and k3s enforces them out of the box (verified). The rules are
  stricter than "local network": each component can reach only what it needs
  (least privilege).
- **Trade-off:**
  - NetworkPolicies work at L3/L4, so they cannot filter by domain name.
  - Allowing DNS leaves a theoretical DNS-tunnelling channel through CoreDNS
    forwarding to upstream resolvers. Listed as an open item.
  - Enforcement depends on the CNI, so another cluster needs a
    policy-enforcing CNI.
  - In k3s a new pod can run for a few hundred milliseconds before its
    policies apply (k3s issue #14711), hence the wait in `verify-boundary`.
  - A site whose internet access goes through a proxy on a private address
    needs an exception in `values.yaml`.

### A6. Credentials for hashtag search

- **Requirement:** subscriptions to hashtags; how to access Bluesky is not
  specified.
- **Facts (verified 2026-09-30; they correct what step 0 recorded):**
  - `app.bsky.feed.searchPosts` answers:

    | Host | Result |
    |---|---|
    | `public.api.bsky.app` | 403, with or without a token |
    | `api.bsky.app` without a token | 200 today |
    | `api.bsky.app` with a token | 500: these direct AppView hosts "do not support authentication" (Bluesky's rate-limit guide) |
    | `bsky.social` (the entryway) | 401 `AuthMissing` without a token |

  - The documented authenticated path is to log in with
    `com.atproto.server.createSession` at `bsky.social`, then send requests
    to the account's PDS, which forwards them to the AppView.
  - Bluesky blocks unauthenticated search on purpose, to reduce load, and
    turns the block on and off. A Bluesky contributor says so in
    bsky-docs #332. On 2026-08-18 `api.bsky.app` was blocked as well.
  - `createSession` is limited to 30 per 5 minutes and 300 per day per
    account.
- **Options:**
  - A. Credentials required: without them, no hashtags.
  - B. Unauthenticated search only, on `api.bsky.app`.
  - C. Hybrid: credentials when provided, otherwise unauthenticated search.
  - D. The public firehose (Jetstream), filtering hashtags locally, with no
    credentials.
- **Decision:** **C, hybrid** (the author's choice).
  - Credentials are optional, in a git-ignored `.env`, turned into a
    Kubernetes Secret that exists only in `ingest` and that only the hashtag
    ingestor mounts.
  - With credentials, it logs in and searches through the PDS.
  - Without them, it searches `api.bsky.app` directly. Bluesky's 403 is
    then a warning that says how to add credentials, not a failure.
  - The details are in D20.
- **Why:**
  - The reviewer can try hashtags without a Bluesky account while Bluesky
    allows it, and with a `.env` it always works.
  - The secret never reaches the analysis zone, nor the handle ingestor.
  - A relies on the reviewer having an account.
  - B depends on a block that Bluesky toggles.
  - D is a continuous, high-volume stream that needs a long-running
    consumer.
- **Not done on purpose:** the 403 can be avoided by changing the case of
  the method name in the URL (#332). That would deliberately bypass
  Bluesky's load control, so it is not used.
- **Trade-off:**
  - Two code paths to test.
  - Without credentials, hashtags stop updating whenever Bluesky turns the
    block on. The warning, and the summary's `updated_at`, make that
    visible.

### A7. Local platform and database

- **Requirement:** Kubernetes, on-premises deployment, high availability.
- **Options:**
  - Cluster: k3d (k3s in Docker), kind, minikube, k3s on a VM.
  - Database: the official PostgreSQL image with our own StatefulSet, the
    Bitnami chart, the CloudNativePG operator, or an external database.
- **Decision:** **k3d with 1 server and 2 agents**, k3s pinned to
  `v1.36.4-k3s1`. **PostgreSQL from the official image** with our own
  StatefulSet: a single instance with a PVC. CloudNativePG is an open item.
- **Why:**
  - k3s ships an embedded NetworkPolicy controller (kube-router), so policies
    are enforced with no extra CNI (verified). With other local
    distributions, enforcement depends on the chosen CNI and would need
    separate verification.
  - k3s is also a real on-prem distribution, so the same stack carries over
    from the laptop.
  - Two agents allow spreading replicas and draining a node to demonstrate
    high availability. Pinning the k3s version makes the setup reproducible.
  - Bitnami retired its free catalogue (verified). The official image plus a
    small StatefulSet is transparent and has no extra dependencies.
    CloudNativePG gives failover but adds an operator and CRDs to install.
- **Trade-off:** the single PostgreSQL instance is a single point of failure:
  the API tier is highly available, the database is not (details, upgrade
  path and how to scale it: D14). The k3d "nodes" are
  containers on one host, so node failure is only simulated. Their IPs can
  change on restart (see D11).

### A8. How ingestion and summarisation are scheduled

- **Requirements:** nothing about freshness or scheduling.
- **Options:** Kubernetes CronJobs; long-running Deployments with an internal
  loop; queue-driven workers; a streaming consumer of the firehose.
- **Decision:** the ingestor and the summary worker run as **CronJobs** with
  `concurrencyPolicy: Forbid`.
- **Why:** polling fits the Bluesky endpoints in use; `Forbid` prevents
  overlapping runs (duplicate work, rate limits) with no leader election; a
  failed run is retried on the next schedule; resources are released between
  runs, which matters for CPU inference.
- **Trade-off:** data freshness is bounded by the schedule (not real time);
  every run pays the start-up cost; Job history needs limits.

### A9. Classify each post once

- **Requirements:** nothing about how posts are classified.
- **Options:** re-classify every recent post on each run; classify each post
  once and store the result; classify at ingestion time, which would give the
  ingest zone access to the LLM and cross the boundary.
- **Decision:** each post is classified once and the result is stored in
  `post_sentiments`, a table that only `analysis` writes. `posts` is
  read-only for `analysis`.
- **Why:** the LLM on CPU is the bottleneck, so classifying once avoids
  repeated work. Classification stays inside the analysis zone. The database
  grants mirror the network flow: ingest writes posts, analysis reads them.
- **Trade-off:** a change of model or prompt does not re-classify old posts
  unless the stored results are invalidated.

### A10. Delivery strategy within the timebox

- **Requirement:** about one evening of work, with whatever is unfinished
  recorded as open items; `make build` and `make start`.
- **Options:** build all features in breadth; build an end-to-end slice
  first and cut in a fixed order.
- **Decision:** the Makefile grows incrementally from step 3 and stays
  portable to macOS. An end-to-end slice comes first. If time runs out, cut
  in this order: the LLM sentence → the node-drain demo → hashtags. The time
  spent is reported honestly in `DESIGN.md`.
- **Why:** a working slice is worth more than several half-finished
  features. The cut order drops the least important feature first. The
  reviewer may run macOS.
- **Trade-off:** each cut removes, in turn, readability, visible evidence of
  high availability, and half of requirement 1. The full plan goes beyond one
  evening, and the time report says so.

### A11. Development environment

- **Requirements:** nothing about it; the user's machine is unknown (possibly
  an ARM Mac).
- **Options:** native Windows with Docker Desktop; WSL2 with Docker Desktop
  integration; WSL2 with Docker Engine inside the distribution; a Linux VM.
- **Decision:** work in **WSL2 (Ubuntu 24.04)** with the repository on the
  Linux filesystem (`~/social-signal`), and force LF line endings with
  `.gitattributes` (`* text=auto eol=lf`).
- **Why:** the same Linux tooling the reviewer will use; no Windows path
  problems (spaces and accents broke `make`); no CRLF breaking scripts; the
  Linux filesystem is much faster than `/mnt/c` for Docker builds.
- **Trade-off:** WSL-specific quirks, such as the distribution shutting down
  when idle (see [`PROGRESS.md`](PROGRESS.md#how-to-resume)).

## 2. Other design decisions (step 0)

### D1. Database roles and migrations

- **Decision:** three PostgreSQL roles:
  - `ingestor`: reads subscriptions, writes posts.
  - `analysis`: manages subscriptions, reads posts, writes `post_sentiments`
    and summaries.
  - `migrator`: the only role with DDL.

  Migrations use **Alembic**, run by a Job in `data` as a Helm
  `pre-install` / `pre-upgrade` hook.
- **Alternatives:** one shared application user; running migrations at
  application start-up; manual migrations.
- **Why:** least privilege at the database level complements the network
  policies. Running migrations before the new pods roll out gives one
  migration per release, and the application roles cannot change the schema.
- **Trade-off:** a Helm rollback does not undo migrations, so they must be
  backward compatible (expand / contract) to allow rolling updates.
- **Correction (step 4a).**
  - *Problem:* Helm runs `pre-install` hooks "before any resources are
    created" (Helm docs). With PostgreSQL in the same chart, the first
    install's migration would have no database to connect to. The agent
    found this before implementing anything.
  - *Fix:* PostgreSQL is a release of its own, installed first (D2), so the
    application's hook always finds the database.
  - *Where the roles come from:* PostgreSQL's init script, which runs once on
    an empty volume. It creates the three login roles and the database
    `socialsignal`, owned by `migrator`. `ingestor` and `analysis` only get
    `CONNECT`; tables and per-table grants come from the migrations
    (step 4b).
  - *Verified:* none of the three roles is superuser or can create roles or
    databases.

### D2. One Helm chart for the three namespaces

- **Decision:** a single chart deploys `ingest`, `data` and `analysis`.
- **Alternatives:** one chart per zone; an umbrella chart with subcharts;
  Kustomize or raw manifests.
- **Why:** one release gives one version of the whole system, atomic
  upgrades and one values file, which is simpler for the reviewer.
- **Trade-off:** the zones cannot be upgraded independently. The chart
  creates resources in several namespaces, so installs and uninstalls need
  care.
- **Implementation (step 3c):**
  - Every template sets its namespace explicitly. The release metadata is
    stored in `default`, because the release has no single "home" zone and
    the namespaces belong to the platform layer (D7).
  - `make start` runs `helm upgrade --install … --wait`; bare `--wait` means
    the `watcher` strategy in Helm 4 and is also valid in Helm 3.
  - Namespace names are values, and they must match `deploy/platform`.
- **Revised (step 4a): two charts, two releases.**
  - `socialsignal-db`, in `data`: PostgreSQL and its ingress policy.
  - `socialsignal`, metadata in `default`: everything else.

  `make start` installs the database first.
  - *Why:*
    - The migration hook needs the database to exist (D1).
    - Data and stateless applications have different lifecycles: upgrading
      or uninstalling the application never touches the database, and a
      PostgreSQL upgrade is a `helm upgrade` of its release only.
    - The application reaches the database by its Service name, so it does
      not care how the database is deployed.
  - *Trade-off:* two releases to keep in step. The data zone's policies
    live in the database chart: `postgres-clients`, and since step 4b
    `migrator-egress` (D16). The clients' matching egress rules stay in the
    application chart.
  - *Step 4b:* `make start` now calls `scripts/deploy.sh`, which installs
    both releases and passes the application images from the bundle's
    `images.txt`.

### D3. Ingress through Traefik

- **Decision:** the UI is exposed through **Traefik** (bundled with k3s),
  reached through a k3d port mapping. The browser never talks to the API pods
  or the LLM directly.
- **Alternatives:** another ingress controller; `kubectl port-forward`;
  NodePort services.
- **Why:** Traefik is already in k3s, so there is nothing extra to install.
  A single entry point lets the API policy accept ingress only from Traefik.
- **Trade-off:** the API policy depends on Traefik's namespace and labels.

### D4. Getting images into the cluster: offline image bundle (step 3a)

- **Decision:** `make build` downloads every third-party image, pinned to an
  exact version, and saves it as a tarball under `dist/images/<arch>/`.
  `make start` (step 3b) runs the cluster from that bundle only:
  - `k3s/`: the k3s air-gap images (CoreDNS, Traefik, pause…), checked
    against the release's official sha256 file and mounted into every node.
    k3s imports them every time it starts.
  - `node/`: the k3s node image and the k3d helper images, loaded with
    `docker load`. k3d pulls an image only when it is missing locally, and
    the helper images are pinned with `K3D_IMAGE_LOADBALANCER` /
    `K3D_IMAGE_TOOLS`.
  - `workload/`: images for our pods, imported into the nodes with
    `k3d image import`.

  At deploy time the only outbound traffic is the ingestor's access to
  Bluesky. The application images built in later steps are added to the same
  bundle.
- **Alternatives:**
  - Pull from public registries at deploy time: the simplest, but the site
    needs Docker Hub and GHCR access.
  - A local registry that images are pushed to: k3d-managed on the laptop, or
    a Harbor-like registry on site.
  - `k3d image import` straight from the local Docker cache, with no bundle
    on disk: nothing to carry to another host.
- **Why:**
  - The deployment host needs no registry access, which is the on-prem /
    air-gapped delivery story.
  - Within the timebox, a directory of tarballs is simpler than running a
    registry (the author's call).
  - Every image is pinned, and the k3s tarball is checksum-verified.
  - The cluster is also configured so it *cannot* pull (D9), which makes the
    guarantee checkable on a connected laptop.
- **Trade-off:**
  - `k3d image import` copies each image into all three nodes. For the
    multi-GB LLM image this triples disk usage and import time.
  - A rebuilt image has to be re-imported, so tags must change on every
    build; never `latest`.
  - The bundle is per architecture; use `ARCH=arm64` to build one for an ARM
    host.
  - `dist/` is not in the zip (hundreds of MB now, GBs with the LLM), so the
    reviewer generates it with `make build`.
  - Images are pinned by tag rather than digest, and the tarballs are not
    signed (open item).
  - On a site that has its own registry, the same tarballs would be pushed
    there instead.

### D5. Bluesky endpoints and idempotent ingestion

- **Decision:**
  - Handles: `app.bsky.feed.getAuthorFeed` on `public.api.bsky.app`,
    unauthenticated.
  - Hashtags: `app.bsky.feed.searchPosts`. With credentials it goes through
    the account's PDS, after logging in at `bsky.social`; without them,
    unauthenticated to `api.bsky.app` (A6, D20). *Corrected in step 6: this
    line used to say "on `api.bsky.app` with a Bearer token", which that
    host does not support.*
  - Writes are idempotent, keyed on each post's URI.
- **Alternatives:** the firehose or Jetstream; a third-party AT Protocol
  SDK.
- **Why:** these are documented XRPC endpoints that are simple to poll.
  Idempotent writes make retries and overlapping schedules harmless.
- **Trade-off:** rate limits and polling latency.

### D6. Reviewer prerequisites

- **Decision:** `docker`, `k3d`, `kubectl`, `helm` and `make`, plus `curl`
  and `shasum`, which are preinstalled on macOS and most Linux distributions.
  `uv` is only needed for local development: Python dependencies are
  installed inside the Docker builds.
- **Alternatives:** require a local Python and uv toolchain.
- **Why:** fewer tools for the reviewer to install; builds match the
  reviewer's CPU architecture.
- **Trade-off:** slower builds, which Docker layer caching mitigates.

### D7. Platform layer outside the Helm release (step 3b)

- **Decision:** `make start` creates the namespaces (`ingest`, `data`,
  `analysis`) and a `default-deny-all` NetworkPolicy in each of them with
  `kubectl apply -f deploy/platform/`. The Helm chart (step 3c on) only holds
  the per-component allow rules and the workloads.
- **Alternatives:** create the namespaces and the default-deny policies from
  the chart itself.
- **Why:**
  - `helm uninstall` can never delete a namespace, and with it the PostgreSQL
    volume; Helm handles namespaces it owns awkwardly.
  - The security baseline exists before any workload is deployed.
  - It mirrors a real split: a platform team owns namespaces and baseline
    policies, the application team owns the chart.
- **Trade-off:** two mechanisms (kubectl and Helm) instead of one. The
  default-deny policies are not versioned with the chart.

### D8. Local cluster access: localhost only, context untouched (step 3b)

- **Decision:**
  - The Kubernetes API listens on `127.0.0.1:6445` and Traefik on
    `127.0.0.1:8088`, so nothing is exposed to the host's network.
  - k3d is told not to switch the current kubectl context
    (`switchCurrentContext: false`), and every script passes
    `--context k3d-socialsignal`.
  - Traefik is not on 8080: kubectl with no context falls back to
    `localhost:8080`, and it would then talk to Traefik and produce confusing
    errors. The author found this by running `kubectl` before the cluster
    existed.
- **Why:** the reviewer's machine may have other clusters and contexts, and
  running the demo must not change them.
- **Trade-off:** to use kubectl by hand you pass `--context` or switch
  explicitly. k3d still sets the context when the kubeconfig has no current
  context at all (verified in its source), which overwrites nothing.

### D9. The cluster cannot pull images (step 3b)

- **Decision:** every registry is mirrored to `https://offline.invalid` in
  k3s' `registries.yaml`: the wildcard `*` plus explicit `docker.io` and
  `ghcr.io` entries. k3s runs with `--disable-default-registry-endpoint`, so
  containerd cannot fall back to the real registry. Images come only from the
  offline bundle (D4).
- **Context:** the first `make start` showed that k3s imports the air-gap
  tarball *asynchronously*, which took about 3.5 minutes per node on this
  HDD. The kubelet started the system pods before the import finished and
  silently pulled their images from Docker Hub. Offline, those pods would
  just have waited, but on a connected host the "no downloads" promise
  could not be proven.
- **Alternatives:** accept and document the silent pulls on connected hosts.
- **Why:**
  - The promise is enforced by the infrastructure rather than hoped for,
    like the network boundary.
  - A connected laptop now behaves exactly like an isolated site.
  - An image missing from the bundle fails visibly (`ErrImagePull`) instead
    of being fetched.
- **Trade-off:**
  - On first creation the system pods wait for the import, so `make start`
    takes about 4.5 minutes on this HDD.
  - k3s re-imports the tarball on every start. That costs time but does not
    block, because the images are already in containerd.
  - Adding an image means adding it to the bundle; there is no escape hatch.
- **Verified:** after creation there are 0 `Successfully pulled` events and
  every `Pulled` event reads "already present on machine". Test pods with
  `docker.io/library/busybox:1.36` (explicit mirror) and
  `registry.k8s.io/pause:3.10` (wildcard only) both end in `ImagePullBackOff`
  against `offline.invalid`.

### D10. `make clean` keeps the image bundle (step 3b)

- **Decision:** `make clean` deletes the cluster only; `make distclean` also
  deletes `dist/`.
- **Alternatives:** `make clean` deletes everything.
- **Why:** on an isolated host the bundle cannot be downloaded again, so the
  everyday cleanup must not destroy it. The bundle will also reach several
  GB once the LLM image is added.
- **Trade-off:** one more target to explain.

### D11. `make start` waits for stable nodes before importing (step 3b)

- **Decision:** before importing workload images, `scripts/cluster-up.sh`
  waits until containerd answers on every node and every Node is `Ready`,
  three checks in a row. After the import it checks that each image is on
  every node.
- **Context:** after `make stop` and `make start`, Docker can give an agent
  a new IP. k3s then crash-loops ("network policy controller: failed to find
  interface with specified node ip") for one or two minutes until the Node
  object is updated. The first version of the script imported during that
  window and failed. `k3d image import` only logs a per-node failure and
  still exits 0 (verified in its source), which is why the script checks the
  result itself.
- **Alternatives:** static node IPs, which were not verified to be possible
  with k3d.
- **Trade-off:** a restart takes about 2 minutes on this machine.

### D12. How `make verify-boundary` tests the policies (step 3c)

- **Decision:**
  - `scripts/verify-boundary.sh` starts one curl pod per component identity
    (ingestor, api, worker, llm). Each carries that component's
    `app.kubernetes.io/component` label, so exactly the same NetworkPolicies
    apply to it as to the real pods.
  - It waits 5 s (k3s #14711), runs the checks with `kubectl exec`, prints
    a PASS/FAIL table, deletes the pods and exits 1 on any failure.
  - There are two kinds of check:
    - DNS: `timeout 5 nslookup <name>.`, giving *resolves* or *no-dns*.
    - Connection: the curl exit code, where 0 = *open* and 7/28 =
      *blocked*.
- **Alternatives:**
  - `kubectl exec` into the real pods: needs curl in the application
    images, and they do not exist yet.
  - `kubectl debug` ephemeral containers in the real pods: tests the real
    network namespace, but the containers stay in the pod spec until it
    restarts, and it also needs the real pods.
- **Why:**
  - It works from step 3 on, independently of the application images.
  - It exercises the real policies in the real cluster, not a simulation.
- **Trade-off:**
  - It proves the policy attached to a *label*, not to a specific running
    pod. The chart must give the real pods the same component labels.
  - The Services added later must select an extra label (e.g.
    `app.kubernetes.io/instance`), so that a test pod never receives real
    traffic.
- **Lesson:** the first version used curl's exit codes alone and failed on
  the LLM pod. A dropped DNS query and a dropped connection both end in a
  timeout (exit 28), so DNS is now checked separately. For the API,
  *resolves* plus *blocked* proves that the policy, not DNS, stops it.
- **Extended (step 4a):**
  - A third kind of check, *tcp*, uses curl's `time_connect` on a
    `telnet://` URL: a completed TCP handshake means *open*. PostgreSQL never
    answers a bare connection, so the exit code would say nothing.
  - An *outsider* pod in `default`, which has no policies and open egress,
    must be blocked by the database's own ingress rule.
  - Result: 16/16 checks pass in about 40 s.
- **Extended (step 4c):** database privilege checks from each zone, with
  that zone's own credentials (D17): 27 checks in about 45 s.
- **Extended (step 7b):** four *tcp* checks against the LLM Service. The
  worker is *open*. The API (same zone), the ingestor and the outsider are
  *blocked*; the outsider's egress is open, so its result proves the LLM's
  own ingress rule. 31 checks in about 60 s.

### D13. Database credentials are generated by `make start`, outside Helm (step 4a)

- **Decision:** `scripts/db-secrets.sh` creates random 32-character
  passwords from `/dev/urandom`, on the target cluster. Each zone only
  receives its own role:
  - `data/postgres-credentials`: every password, because PostgreSQL's init
    script needs them all;
  - `data/db-migrator`, `ingest/db-ingestor` and `analysis/db-analysis`:
    `username` and `password` of that role only.

  Existing Secrets are kept. If the master Secret is missing but the
  database volume exists, the script refuses to continue, because new
  passwords would not match the roles stored in the volume.
- **Alternatives:**
  1. Helm generates them (`randAlphaNum` + `lookup`). Helm stores
     everything it renders, passwords included, in the release's Secret.
     `lookup` does not work with `helm template` or a dry-run, and the
     database chart would have to create Secrets in other zones.
  2. **Generated by `make start` (chosen).**
  3. A user-provided `.env`. Nobody needs to know these passwords, the
     reviewer would have to create the file, and it could be committed by
     mistake. It remains the plan for the user's own Bluesky credentials
     (A6, step 6).
  4. An external secret manager (Vault, External Secrets Operator, Sealed
     Secrets, SOPS). This is the production answer, with rotation and audit,
     but it means more components, and an on-prem instance in an isolated
     site. Open item.
- **Why:** the passwords never pass through the repository, the image
  bundle or a Helm release, and each zone can only mount its own. This fits
  the platform layer (D7).
- **Trade-off:**
  - It is one more imperative step, and rotation is manual.
  - Kubernetes Secrets are only base64-encoded in k3s' datastore (SQLite on
    the server node). k3s can encrypt them at rest with
    `--secrets-encryption` (the flag exists and is currently disabled). Not
    enabled: it is an open item.
- **Verified:**
  - over the network, each role logs in only with the password in its own
    Secret; a wrong password, or another role's, is rejected;
  - no password appears in the pod spec or in either Helm release (manifest
    or values);
  - passwords travel through stdin only: the `kubectl create -f -` heredoc,
    and psql's backquote `\set` in the init script.

### D14. PostgreSQL: one pod, how it would be upgraded and scaled (step 4a)

- **Decision:**
  - `postgres:18.6-alpine3.23`. PostgreSQL 19 is not on Docker Hub yet.
  - A StatefulSet with **1 replica** and a 1 Gi PVC (k3s `local-path`).
  - Non-root: uid/gid 70, the Alpine image's `postgres` user. No
    capabilities, no privilege escalation, seccomp `RuntimeDefault`, no
    ServiceAccount token.
  - `pg_isready` startup, readiness and liveness probes.
  - A `postgres` ClusterIP Service for clients, plus a headless Service for
    the StatefulSet.
- **Why one pod:** the timebox, and the brief's focus on HA *for the
  analysts*: the API is replicated, the database is not. The consequence
  is stated plainly: **today any restart or upgrade of PostgreSQL is an
  outage**. Deleting the pod measured about 6 s until it was Ready again,
  with its data intact. During that window the API cannot read, and the
  CronJobs fail and retry on their next run. Adding replicas to this
  StatefulSet would not help: they would be independent databases, not
  replicas.
- **How it would be upgraded** (documented, not implemented or tested):
  - *Minor version* (18.6 → 18.7), same on-disk format: change
    `POSTGRES_IMAGE`, then `make build` and `make start`. Only the database
    release changes; the application release has no diff, so none of its
    pods restart. Outage: one pod restart.
  - *Major version* (18 → 19). The data directory is incompatible, and the
    image does not convert it. Three options:
    1. `pg_upgrade --link` in a Job, with an image carrying both versions'
       binaries (`tianon/postgres-upgrade:17-to-18` exists; `18-to-19` does
       not yet). PostgreSQL 18's version-specific `PGDATA`
       (`/var/lib/postgresql/18/docker`) lets both versions live in the same
       volume. Outage: minutes.
    2. Dump and restore into a new StatefulSet, then switch the Service
       (offline blue/green).
    3. Logical replication into the new instance, then switch (online
       blue/green). Near-zero outage, much more complex.
- **How it would scale:** the CloudNativePG operator (open item): a primary
  plus streaming replicas, automatic failover, and a Service that always
  points to the primary. The applications would not change, because they
  use the Service name. According to CNPG's documentation, a minor upgrade
  is a rolling update, replicas first and then a switchover of the primary.
  A major upgrade is either an offline in-place `pg_upgrade` or a
  logical-replication blue/green.
- **Trade-off / notes:**
  - The official image trusts `local` and `127.0.0.1` connections without a
    password (its default `pg_hba.conf`). Anyone who can `kubectl exec`
    into the pod is superuser, which cluster admins are anyway. Every
    network client must use SCRAM-SHA-256.
  - `local-path` pins the volume, and so the pod, to one node.

### D15. Python images: one Dockerfile, tagged by content (step 4b)

- **Decision:**
  - `docker/python-service.Dockerfile` builds every Python service,
    parametrised by `PACKAGE` and `SERVICE_DIR`. It follows uv's Docker
    guide:
    - uv 0.12.21 copied from its image;
    - a dependencies-only layer (`uv sync --frozen --no-install-workspace`)
      that stays cached until `uv.lock` changes;
    - then the service plus `packages/`, installed `--no-editable`;
    - a final stage on `python:3.12.14-slim-trixie` with only the `.venv`,
      running as uid 10001, with no uv and no sources.
  - Only the service's own directory is copied, so a change in another
    service neither rebuilds the image nor changes its tag.
  - `.dockerignore` is an allow-list (`pyproject.toml`, `uv.lock`,
    `packages/`, `services/`): `.git`, `dist/`, docs and any `.env` never
    reach the build.
  - The tag is **the first 12 hex digits of the image ID**, a hash of its
    content (the author chose option A). `scripts/build-images.sh` saves the
    image to `dist/images/<arch>/app/` and writes the reference to
    `images.txt`, which `make start` imports and passes to Helm. Git's
    revision goes in a comment in `images.txt`, not in the image, where a
    label would change the tag on every commit.
- **Alternatives for the tag:**
  - B, the git commit: readable, but fails without `.git` (the zip may not
    have it), and uncommitted changes need a `-dirty-<time>` suffix that
    changes on every build.
  - C, the version in `pyproject.toml`: most readable, but it must be bumped
    by hand, and a forgotten bump leaves nodes running the old image.
- **Why:**
  - The cluster cannot pull and uses `IfNotPresent` (D9), so a reused tag
    would keep running the old code.
  - Helm only rolls out when the rendered spec changes.
  - A content tag changes *if and only if* the image changes, with no
    dependency on git or on human discipline.
- **Lesson (found by testing):** the first two builds of identical code got
  different tags. BuildKit adds a provenance attestation, with per-build
  metadata, to the image index, so the index ID never repeats even though
  the `linux/amd64` image inside is identical. The build now uses
  `--provenance=false --sbom=false`.
- **Verified:**
  - three builds in a row give the same tag;
  - a change in another service keeps the tag; a change in the service or
    in `packages/common` changes it; reverting gives back the original tag;
  - the image runs as uid 10001, with no uv and no `/src`, and works with a
    read-only root filesystem.
- **Trade-off:**
  - Tags are not human-readable. Combining a release version with the
    digest is an open item.
  - Old tags accumulate in the nodes' containerd until kubelet's image GC
    removes them.
  - Building for another architecture (`ARCH=arm64` on amd64) needs QEMU
    emulation, which this WSL host lacks (`systemd-binfmt` fails). Reviewers
    build natively.
  - Without the attestations there is no build provenance; signing the
    bundle is an open item.

### D16. Schema migrations: Alembic in a Helm hook Job (step 4b)

- **Decision:**
  - `services/migrations` (`socialsignal-migrations`: alembic 1.20.0,
    SQLAlchemy 2.1.1, psycopg 3.3.6) runs as
    `python -m socialsignal_migrations`.
  - Alembic is configured in code: no `alembic.ini`, the connection comes
    from the environment, the password from a mounted file, and
    `lock_timeout=10s` / `statement_timeout=60s` so it never waits forever
    on a lock.
  - In the application chart it is a `pre-install,pre-upgrade` hook Job in
    `data`:
    - non-root, read-only root filesystem, no ServiceAccount token;
    - `backoffLimit: 2`, `activeDeadlineSeconds: 300`;
    - `before-hook-creation`, so the last Job and its logs stay until the
      next run.
  - Revision `0001` creates `subscriptions`, `posts`, `subscription_posts`,
    `post_sentiments` and `summaries`, with the per-role grants the author
    approved. All tables are owned by `migrator`; nothing is granted to
    `PUBLIC`.
- **Second hook ordering issue:** the Job's own NetworkPolicy was in the
  application chart. On a first install the hook would run before it
  exists, and default-deny would cut it off. It moved to the database
  chart, which is installed first, as `migrator-egress`. It got a new name
  because an existing cluster already had a `migrator` policy owned by the
  application release, and Helm refuses to adopt it.
- **Why:** migrations run exactly once per release and *before* any new
  application pod. If they fail, Helm aborts the release and no new code is
  rolled out.
- **Verified:**
  - the first run applies `0001` (tables, owner and grants as designed);
  - a new image re-runs the hook as a no-op;
  - forcing a failure (a non-existent database) made Helm report
    `pre-upgrade hooks failed`. The release was marked failed and the
    previous revision kept serving; `make start` recovered it.
- **Trade-off:**
  - Rollbacks do not undo migrations, so each one must be backward
    compatible (expand/contract).
  - Hook Jobs are not managed as part of the release (Helm docs).
  - The grants are tested by `make verify-boundary` since step 4c (D17).

### D17. Database privilege checks in `make verify-boundary` (step 4c)

- **Decision:**
  - Two more test pods run the `postgres` image, which is already in the
    bundle and ships `psql`:
    - `vb-db-ingestor` in `ingest`, with the ingestor's labels and the
      `db-ingestor` Secret;
    - `vb-db-analysis` in `analysis`, with the API's labels and the
      `db-analysis` Secret.

    Each logs in through the `postgres` Service with its own zone's
    credentials, so the same NetworkPolicies apply and SCRAM is enforced
    (never `127.0.0.1`, D14). Both pods are non-root (uid 70), with no
    capabilities, a read-only root filesystem and no ServiceAccount token.
    They are created from a manifest because `kubectl run` cannot read an
    environment variable from a Secret.
  - A fourth kind of check, *sql*, runs its SQL inside `BEGIN … ROLLBACK`,
    so it never commits anything:
    - *allowed* means the SQL succeeds;
    - *denied* means it fails with `permission denied`;
    - any other error is a FAIL and its message is printed, so a typo or a
      constraint violation can never pass as *denied*.
  - The ingestor can read `subscriptions` and insert the same post twice
    (idempotent). It cannot read `summaries`, write `post_sentiments`,
    delete subscriptions or create tables.
  - Analysis can read `posts` and `subscription_posts`, subscribe (identity
    column plus `RETURNING`) and upsert a summary twice, which exercises
    both the insert and the update paths. It cannot insert posts or create
    tables.
  - **One scenario needs both roles in turn**, because the ingestor can only
    link a post to a subscription that the analysis zone created. It runs as
    a single rolled-back transaction inside `postgres-0`, where the
    superuser switches identity with `SET LOCAL ROLE` before each step. The
    steps are:
    1. analysis subscribes;
    2. the ingestor stores a post and links it;
    3. analysis classifies the post and writes the summary;
    4. analysis unsubscribes.

    Afterwards the link and the summary must be gone, while the post and
    its label remain.
- **Alternatives:**
  - Run everything as the superuser with `SET ROLE`. It is simpler, with no
    extra pods, but it proves neither that each zone's Secret holds the
    right role nor that the login works over that zone's network path.
  - pgTAP: a real test framework, but it means installing an extension in
    the database and adding one more image to the bundle.
  - Commit real test rows and delete them afterwards. Only `migrator` may
    delete a post, so a test post would stay in the production tables.
- **Why:**
  - NetworkPolicies are the first layer. The grants are the second: they
    limit what a compromised zone can do even over a valid connection.
  - Running the checks from each zone, with only the credentials that zone
    holds, tests the network path, the credentials and the grants together.
- **Findings (by testing):**
  - `INSERT … ON CONFLICT (uri) DO NOTHING` fails for the ingestor, because
    naming a conflict target requires `SELECT` on its columns (PostgreSQL
    docs). Without a target, `INSERT` alone is enough and a repeated insert
    does nothing.
  - The only unique constraint on `posts` and on `subscription_posts` is the
    primary key, so both forms behave the same. **The ingestor will use
    `ON CONFLICT DO NOTHING` without a target (step 5)**, and the grants
    stay as they are. The alternative, `GRANT SELECT (uri) ON posts`, would
    let the internet-facing zone find out which posts exist.
  - The identity column needs no privilege on its sequence:
    `subscriptions_id_seq` has no grants at all.
  - Foreign-key checks and `ON DELETE CASCADE` need no privileges on the
    other table. The ingestor links to a post it cannot read, and the
    analysis role's delete removes links from `subscription_posts`, where it
    has no `DELETE`. Referential actions run with the table owner's
    privileges.
- **Verified:**
  - 27/27 checks pass in about 45 s. Afterwards every table is still empty
    and no test table exists.
  - **Sabotage test:** `GRANT SELECT ON summaries TO ingestor` made exactly
    that check fail (`expected denied, got allowed`), and `make` exited
    non-zero. After the `REVOKE`, `\dp` matched the saved copy and the run
    passed 27/27 again.
- **Trade-off:**
  - The lifecycle scenario is the only check that uses the superuser. It
    runs through `kubectl exec` into the database pod and the local socket,
    which the image trusts. That is acceptable because it tests privileges,
    not authentication.
  - The analysis psql pod uses the API's label; the worker uses the same
    database role.
  - Each psql pod has its role's password in its environment. Anyone who
    can read it there can already read the Secret.
  - As with D12, the checks prove what a label and a Secret allow, not what
    a particular running pod does.

### D18. Handle ingestor: what it fetches and how it stores it (step 5a)

- **Decision:**
  - **What is fetched.** On each run (A8), every `handle` subscription gets
    one call to `app.bsky.feed.getAuthorFeed` on `public.api.bsky.app`: one
    page of 50 items, with no pagination (A2).
    - `filter=posts_and_author_threads`: the account's posts and its own
      threads, but **not its replies to other accounts** (the author's
      decision).
    - Reposts are dropped in code, because every filter includes them.
      Posts without text (only an image or a link) are dropped too.
  - **`created_at` = `min(record.createdAt, indexedAt)`.** `createdAt` is
    set by the author's client; `indexedAt` is when Bluesky received the
    post.
  - **The response is untrusted input:**
    - each item is validated and a malformed one is skipped and counted,
      never stored;
    - timestamps must carry a time zone;
    - identifiers must be non-empty strings;
    - NUL characters, which JSON allows and PostgreSQL `text` does not, are
      removed from the text.
  - **Settings are validated at start-up:** `limit` must be 1-100, and
    `filter` must be one of the lexicon's values, because Bluesky silently
    ignores an unknown filter. A 400 from Bluesky can then only mean a bad
    subscription.
  - **Writes:**
    - `INSERT … ON CONFLICT DO NOTHING` without a conflict target (D17);
      `rowcount` tells new rows from existing ones without `SELECT`;
    - one transaction per subscription, so one failure never blocks the
      others;
    - a foreign-key violation means the subscription was deleted during the
      run: nothing is stored and the run goes on.
  - **Exit status:**
    - 0 when every subscription was stored, or skipped because Bluesky
      rejected the account (a warning);
    - 1 when a network, Bluesky or database error prevented storing at
      least one subscription (after processing the rest).
  - **Libraries:**
    - httpx 0.28.1: per-request timeouts, retries of failed connection
      attempts only, and `MockTransport` for tests;
    - psycopg 3 with no ORM, through `socialsignal_common.db.connect()`
      (autocommit, with explicit transaction blocks), which the API and the
      worker will reuse.
  - **Tests:** pytest, in `tests/` at the root. `.dockerignore` leaves that
    directory out of the build context, so changing a test never changes an
    image tag (D15).
- **Alternatives:**
  - Filter:
    - `posts_with_replies` (the default) also returns replies to other
      accounts;
    - `posts_no_replies` drops the author's own threads as well.
  - Paginate until the 7-day window is covered.
  - `created_at` from `createdAt` alone, or from `indexedAt` alone.
  - Exit 1 for any problem, unknown accounts included.
  - `urllib` from the standard library; SQLAlchemy for the inserts.
- **Why:**
  - **Replies to other accounts:** without the post they answer, the LLM
    cannot interpret them, and on social networks many are sarcastic. The
    author's own threads are part of what the account publishes.
  - **Measured on `@bsky.app`, last 50 items:**

    | `filter` | Posts | Own threads | Replies to others | Reposts | Oldest |
    |---|---|---|---|---|---|
    | `posts_with_replies` | 7 | 36 | 3 | 4 | late August |
    | `posts_no_replies` | 35 | 0 | 0 | 15 | April |
    | `posts_and_author_threads` | 7 | 35 | 0 | 4 | late August |

  - **One page:** the worker only summarises the last 50 posts, and the
    idempotent writes make the overlap between runs free.
  - **The `created_at` cap:** a future `createdAt` would otherwise keep a
    post among the "most recent" forever. A back-dated one (e.g. an import
    from another network) correctly stays old.
  - **Exit status:** an account that no longer exists would otherwise fail
    every run until someone unsubscribes, hiding real failures.
  - **Validating the filter:** a typo in `values.yaml` would otherwise
    silently bring back the replies to other accounts.
- **Trade-off:**
  - The tone of the author's replies to other accounts is lost. Open item:
    classify them with the post they answer as context.
  - An account that publishes more than 50 items between two runs loses the
    ones in between. The worker only uses the last 50, so the summary is
    not affected.
  - The handle is resolved on every call; a renamed account answers
    "Profile not found". Open item: follow accounts by DID.
  - One HTTP call per handle and run, with no backoff beyond the next
    scheduled run. Many subscriptions could hit Bluesky's rate limits.
- **Verified:**
  - 25 unit tests pass (`uv run pytest`).
  - A real call with the ingestor's client on `@bsky.app` kept 42 posts, all
    by that account, and skipped 4 reposts. An unknown account and a
    malformed handle both raised `ActorError` with Bluesky's message.
  - The database side is tested in step 5b, inside the cluster, with the
    ingestor's real identity. A `kubectl port-forward` would bypass the
    NetworkPolicies and reach PostgreSQL through `localhost`, which the
    image trusts without a password (D14).

### D19. The ingestor runs as a CronJob (step 5b)

- **Decision:** a CronJob `ingestor` in `ingest`, in the application chart.
  - **Schedule:** every 5 minutes (`values.yaml`), with
    `concurrencyPolicy: Forbid`.
  - **`startingDeadlineSeconds: 120`:** a run missed by more than 2 minutes
    (the cluster was stopped, or WSL shut it down) is skipped rather than
    started late.
  - **`backoffLimit: 0`:** no immediate retry; the next scheduled run is the
    retry (A8).
  - **`activeDeadlineSeconds: 240`** (a value): shorter than the interval, so
    a hung run never causes the next one to be skipped under `Forbid`.
  - **History:** the last successful Job and the last 3 failed ones are
    kept, with their logs.
  - **Hardening,** the same as the migration Job:
    - uid 10001, read-only root filesystem, no capabilities, seccomp
      `RuntimeDefault`, no ServiceAccount token;
    - the password is read from the mounted `db-ingestor` Secret, not from
      the environment.
  - **Pod labels:** `app.kubernetes.io/component: ingestor`, which the
    `ingestor` NetworkPolicy selects, plus `app.kubernetes.io/instance`
    (D12).
  - **Settings:** the Bluesky URL, `postsPerHandle` and `authorFeedFilter`
    are values, passed as environment variables and validated by the
    ingestor (D18).
- **Alternatives:**
  - A Deployment with an internal loop. The pod is always running and needs
    its own logic against overlapping runs (A8).
  - `backoffLimit` above 0. Immediate retries against a failing Bluesky add
    load and gain nothing over the next run.
  - A shorter schedule (1 minute) or a longer one (15 minutes).
- **Why:**
  - Five minutes is fresh enough for analysts following a curated set of
    sources. The summaries are recomputed by the worker on its own schedule
    anyway.
  - A curated set of sources means few calls per run.
  - The deadlines keep a stuck or late run from piling up.
- **Trade-off:**
  - Freshness is bounded by the ingestor's schedule plus the worker's.
  - After `make start`, the first run happens at the next 5-minute mark. To
    run it now: `kubectl create job --from=cronjob/ingestor`.
  - The database environment and the security contexts were copied in two
    templates. *Moved into Helm helpers in step 6b (D21).*
- **Verified:**
  - **Image:**
    - `socialsignal/ingestor`, a 50 MB tarball;
    - uid 10001, with a read-only root filesystem and no network;
    - no `/src`, no tests and no uv inside;
    - a wrong filter makes it fail at start-up.
  - **`make start`:**
    - the migrations image got a new tag, because `common` changed, and its
      hook re-ran as a no-op;
    - the CronJob was created;
    - no image was pulled.
  - **End to end, with `bsky.app` and a non-existent account subscribed
    as `analysis`:**

### D20. Hashtag ingestor (step 6a)

- **Decision:**
  - **Same package and image as the handle ingestor, with a subcommand:**
    `python -m socialsignal_ingestor hashtags` (and `handles`). It runs as
    a separate CronJob (step 6b).
  - **Query:** `searchPosts` with `q=#<tag>`, `tag=<tag>` and
    `sort=latest`, one page of 50 (A2).
  - **Replies:** the same rule as for handles (the author's decision). A
    reply is kept only if both the post it answers and the thread's first
    post are by the same author; otherwise it is skipped as "reply to
    others". Search returns no reposts.
  - **Credentials (A6, hybrid):** read from files in a mounted Secret
    (`identifier`, `app-password`).
    - The Secret is optional: a missing or empty directory means no
      credentials. Having only one of the two is a configuration error.
    - **With credentials:** one `createSession` at the entryway
      (`bsky.social`) per run, and only if there are hashtag
      subscriptions. Searches go to the account's PDS, taken from its DID
      document, with the entryway as fallback. Only an `https` URL is
      accepted there, because the token is sent to it. The token is not
      kept between runs.
    - **Without credentials:** search `api.bsky.app` directly.
  - **Outcomes:**
    - A 403 **without** credentials gives one warning that explains how to
      add credentials. The run stops searching, since every request would
      get the same answer, and exits 0.
    - A 403 **with** credentials, a rejected login, or a network or database
      error is a failure: exit 1.
    - A 400 (`BadQueryString`) skips that subscription with a warning.
  - **Secrets:** `Credentials` and `Session` hide the password and the
    token in their `repr`, and nothing logs them.
- **Alternatives:**
  - **One CronJob for both kinds.** The handle ingestor would also receive
    the credentials, and every run would log in: every 5 minutes, 288 of
    the 300 daily logins.
  - **Keep the session between runs** (refresh token). It needs writable
    storage in `ingest`, or a long-running pod, which changes A8. Open item.
  - **`q=*` with the `tag` filter, or `q=#tag` alone.** They returned the
    same posts. `q=#tag` plus `tag` states the intent twice, and does not
    depend on how `*` is parsed.
  - **Look at the parent only to classify a reply.** On the sample it gives
    the same result. The root is checked too, so that a reply inside
    someone else's thread counts as conversation.
- **Why:**
  - A separate CronJob gives least privilege, since only it mounts the
    Secret. It also has its own schedule, and an authentication problem
    never affects handles.
  - The reply rule matches the one for handles and the author's reasons (no
    context, sarcasm). On `@bsky.app` it reproduces the API's own filter
    exactly.
- **Trade-off:**
  - For a very busy hashtag, 50 posts may cover only minutes, and posts
    published between runs are missed. The worker only uses the latest 50
    anyway.
  - Logging in on every run spends part of a daily quota that is shared
    with any other use of the same account.
  - An app password is not read-only: it can act as the account, even
    though the ingestor only reads. OAuth with narrower permissions is an
    open item.
- **Verified:**
  - **53 unit tests pass.** They include the hybrid logic against a fake
    Bluesky:
    - no subscriptions means no login;
    - without credentials, the search goes to the AppView host with no
      `Authorization` header;
    - a 403 without credentials gives a warning after one request, stores
      nothing and exits 0;
    - with credentials, it logs in at the entryway and searches at the PDS
      with the Bearer token;
    - a rejected login fails every hashtag, and so does a 403 with
      credentials.
  - **Real unauthenticated call on `#python`:** `api.bsky.app` kept 50
    posts by 30 authors, covering about 11 hours; `public.api.bsky.app`
    raised `SearchForbidden`.
  - **Real authenticated call, with the author's app password from
    `.env`:**
    - `createSession` at `bsky.social` returned the account's DID and its
      PDS (`*.host.bsky.network`), taken from the DID document;
    - `#python` searched through that PDS with the Bearer token kept 50
      posts by 30 authors;
    - the script printed neither the password nor the token.

### D21. Bluesky credentials Secret and the hashtag CronJob (step 6b)

- **Decision:**
  - **The Secret.** `make start` runs `scripts/bluesky-secret.sh`, which
    turns the optional `.env` into the Secret `ingest/bluesky-credentials`,
    with the keys `identifier` and `app-password`:

    | Contents of `.env` | Result |
    |---|---|
    | No file, or both values empty | The Secret is deleted, if it exists |
    | Only one of the two values | Error |
    | Both values | The Secret is created, or replaced if they changed. Unchanged values keep it as is |

  - **Parsing:** plain `KEY=value` lines. A trailing carriage return (a file
    saved on Windows) and one pair of surrounding quotes are removed.
  - **How the values travel:**
    - only through shell variables, pipes and stdin, never through a
      command's arguments (as in D13);
    - base64 in `data`, so no character can break the YAML;
    - `kubectl create`, never `kubectl apply`. Tested: `apply` copies a
      Secret's `stringData` in clear text into the
      `last-applied-configuration` annotation.
  - **Two CronJobs from one template:**
    - `ingestor-handles`, every 5 minutes;
    - `ingestor-hashtags`, **every 20 minutes** (the author's choice): 72
      logins a day, which leaves over 200 of Bluesky's 300 for manual runs.

    Only `ingestor-hashtags` mounts the Secret, with `optional: true`:
    without it the directory is empty and the search runs unauthenticated.
    The old `ingestor` CronJob was renamed to `ingestor-handles`.
  - **Helm helpers:** the database environment, the credentials volume and
    the security contexts are now shared by the migration Job and both
    CronJobs. The only change in the rendered migration Job is that its
    volume is now named `db-credentials`.
- **Alternatives:**
  - `kubectl create secret generic --from-env-file=.env`. It would store
    every key of the file, with its original names, and it does not remove
    quotes.
  - `kubectl apply` with `stringData`. It is idempotent, but copies the
    password in clear text into an annotation.
  - Helm reading `.env`. The password would be stored in the release,
    which D13 rules out for the database passwords too.
  - A schedule of 10 or 15 minutes (144 or 96 logins a day).
- **Why:** the credentials exist only in the zone that needs them, and only
  in the pod that uses them. They are declared by one file the user
  controls, and removing them is just as easy.
- **Trade-off:**
  - Hashtags are fresh to within 20 minutes, plus the worker's schedule.
  - A changed password is picked up on the next `make start`, not
    immediately.
  - As with the database Secrets, the value is only base64-encoded in k3s'
    datastore (encryption at rest is an open item).
- **Verified:**
  - **Script,** with a fake `kubectl` and fake files: CRLF and quoted
    values, an empty file, a missing file, only one value (error), and no
    final newline.
  - **In the cluster:**
    - the Secret exists only in `ingest`, has no annotations, is in no Helm
      release, and a second run keeps it;
    - only `ingestor-hashtags` mounts it.
  - **End to end with `#python`:**
    - with credentials, it logged in, searched through the author's PDS and
      stored 50 new posts;
    - without them (Secret deleted by the script), the pod started with an
      empty directory, searched unauthenticated and found the same 50 posts
      (0 new);
    - against `public.api.bsky.app`, where Bluesky's block is active, the
      warning came up and the Job ended `Complete` with exit status 0.
  - **The handle CronJob** ran on schedule with the new image.
  - **No leaks:** the app password appears in no CronJob spec, no ingestor
    log and no Helm release.
  - **Also:** `verify-boundary` 27/27, and 0 image pulls.

### D22. The LLM image: Google's QAT GGUF baked into llama.cpp (step 7a)

- **Decision:**
  - **Model:** Google's official `google/gemma-4-E2B-it-qat-q4_0-gguf`,
    file `gemma-4-E2B_q4_0-it.gguf` (3.35 GB).
    - It is quantised to Q4_0 with **quantisation-aware training** (QAT).
    - Licence Apache 2.0, and the repository is not gated.
    - It is pinned to repository revision `675cff42…` and checked against
      its sha256. The multimodal projector (`mmproj`) is not used: we only
      classify text.
  - **Download:** `make model`, part of `make build`, runs
    `scripts/fetch-model.sh`.
    - It downloads to `dist/models/` and resumes an interrupted download.
    - It verifies the sha256, keeps a verified file, and deletes a
      corrupted one.
  - **Image:** `socialsignal/llm`, from `docker/llm.Dockerfile`.
    - It is `FROM ghcr.io/ggml-org/llama.cpp:server-v0.5.0` (amd64 and
      arm64) plus the model at `/models/model.gguf`, with labels that
      record the source file and revision.
    - The build context is only `dist/models/`, and there is no `RUN`, so
      it builds for either architecture without emulation.
    - It is tagged by content and saved to the bundle like our other
      images (D15).
  - **What defines the artefact is fixed in the image's `ENTRYPOINT`:**
    - the model;
    - its API name, `gemma-4-E2B-it-qat-q4_0`, which the worker will store
      with every label;
    - `--offline`, so the server never touches the network;
    - `--no-webui`;
    - the listening address and port.

    Tuning (threads, context size, slots, reasoning) comes from the chart
    as arguments.
  - **Non-root:** the image runs as `USER 10001:10001`. The upstream image
    runs as root.
  - **Output format** (for the worker, step 8):
    - `response_format` in OpenAI's form, `{"type": "json_schema",
      "json_schema": {"name", "schema"}}`, with an `enum` of the three
      labels;
    - the server started with `--reasoning off`;
    - `temperature` 0.
- **Alternatives:**
  - **`ggml-org/gemma-4-E2B-it-GGUF` at Q4_0** (2.84 GB). Quantised after
    training, with no QAT.
  - **Gemma 4 E4B.** A1's fallback, not needed (see *Verified*).
  - **The weights on a volume, or on each node, instead of in the image.**
    Less data to import, but the image would no longer be the single,
    versioned artefact that can be carried into an isolated site (A1, D4).
- **Why:**
  - QAT keeps quality close to the unquantised model at 4 bits.
  - The file comes from the model's publisher, under a clear licence, and
    needs no token.
  - Pinning plus the checksum make the build reproducible and detect
    tampering.
- **Trade-off:**
  - `make build` downloads 3.35 GB the first time, and the bundle grows to
    3.8 GB.
  - Building the image takes about 6 minutes on this HDD, because Docker
    compresses the 3.35 GB layer, plus about 2 minutes for `docker save`.
    That only happens again when the model or the base image changes.
  - The base image is pinned by tag, not digest (open item, as for the
    others).
- **Found by testing:**
  - **`COPY --chmod=0444`** also gave that mode to the `/models` directory
    that BuildKit created. Without the execute bit, the non-root server
    got `Permission denied`. The fix was to drop `--chmod`: the file keeps
    its 0644 mode and is owned by root, so the server can read it but not
    change it.
  - **llama.cpp's server README documents `{"type": "json_schema",
    "schema": …}`.** Version v0.5.0 ignores it: the model answered with its
    own `{"sentiment": …}`. OpenAI's form, and `{"type": "json_object",
    "schema": …}`, are enforced.
  - **`build-images.sh` deleted the previous tarball of an image before
    saving the new one.** A reset of the editor session killed `docker
    save` halfway, and `images.txt` was left pointing to a deleted file. Old
    tarballs, and any interrupted `.part`, are now removed only once the new
    tarball is complete.
- **Verified** (Docker, `--network none`, 4 CPUs, 5 GB memory limit;
  context 8192, 1 slot, 4 threads, reasoning off):
  - **Load:** about 44 s from a cold cache (reading 3.35 GB from the HDD).
    Memory: 3.0 GiB after loading, 3.5 GiB after a long prompt.
  - **Labelled set:** 14 of 14 correct, including two sarcastic posts and
    two in Spanish. A mixed post ("great food, slow service") came out
    negative.
  - **20 real posts from the database:** 18 neutral and 2 positive, which
    is plausible (questions about apples, tech announcements). Every
    answer was a valid label.
  - **Latency per post:** median 2.95 s, maximum 5.5 s.
  - **One summary-sized prompt** (50 posts, 2,573 tokens): 98 s. Prompt
    processing ran at 27 tokens/s and generation at 9 tokens/s. This is a
    preliminary input for step 8: one LLM sentence per subscription and
    run is expensive on CPU.

  The quality run used the first build, started as root only because of
  the permission bug above; the model and server were identical.
  - **The corrected image** (`llm:dec1162d9ccc`) was then checked the way
    the pod will run:
    - uid 10001, read-only root filesystem, no capabilities,
      `no-new-privileges`, `--network none` (only the `lo` interface);
    - `/health` answered 200, and 2.9 GiB of memory after loading;
    - it reproduced the evaluation's answers on the same sarcastic posts.
  - **Sarcasm is fragile and depends on the wording.** "Wow, only three
    hours on hold. Truly world-class service." came out *positive*, with
    both a short prompt and the evaluation's prompt, which names sarcasm.
    With "…on hold with customer support…", as in the evaluation, it came
    out *negative*.

    So 14 of 14 on 15 examples is optimistic. It rules out a useless model,
    but it is not an accuracy figure. This is A1's accepted trade-off, it
    supports excluding replies to other accounts (D18), and a proper
    evaluation set is an open item.
  - **The evaluation is versioned** as `tools/llm_eval.py`, with the
    reworded sarcastic post added as a known hard case. Run as its
    docstring says, on the corrected image: 14 of 15 (only the hard case
    fails), median 2.28 s per post. `tools/` is outside the images' build
    context.

### D23. The LLM in the cluster (step 7b)

- **Decision:**
  - **Deployment `llm` in `analysis`:**
    - **1 replica, `strategy: Recreate`** (the author accepted the
      recommendation);
    - the chart's shared hardening: uid 10001, read-only root filesystem,
      no capabilities, no ServiceAccount token;
    - arguments: 4 threads, an 8192-token context, 1 slot, reasoning off;
    - requests of 1 CPU and 3.5 GiB, limits of 4 CPUs and 4.5 GiB;
    - probes on `/health`: a startup probe that allows up to 5 minutes for
      the model to load, then readiness and liveness.
  - **Service `llm`** on port 8080. It selects `component` and `instance`,
    so verify-boundary's test pod is never an endpoint (D12). The worker
    will use `http://llm.analysis.svc:8080`.
  - **The image is imported into all three nodes**, as every workload
    image is (D4).
  - **`make llm-smoke`** (`scripts/llm-smoke.sh`). From a curl pod with the
    worker's labels, it classifies three unambiguous posts through the
    Service, with the worker's JSON schema, and checks the labels. Sarcasm
    is left to `tools/llm_eval.py` (D22).
  - **`verify-boundary`** gets 4 LLM checks (see D12).
- **Alternatives:**
  - **More replicas, or `RollingUpdate`.** During an update two pods of
    about 4 GiB would run side by side, and neither a small on-prem node nor
    this 10 GB laptop can afford that. Only the batch worker uses the LLM,
    and while it is down the summaries are still served (A3).
  - **Import the image only into one node and pin the LLM there.** It would
    save about 14 GB and two thirds of the import. The LLM could then not
    be rescheduled if its node is drained, which the step 10 demo does.
  - **Smoke test inside `verify-boundary`.** Classification is a
    functional check, not a boundary check.
- **Why:** the analysts use the API, not the LLM, so high availability goes
  where they are (step 10). For the LLM, a short gap in classification
  during an update is acceptable. Fitting in memory is not optional.
- **Trade-off:**
  - An LLM update or crash stops classification for about a minute, while
    the model loads.
  - The first `make start` with a new LLM image spends about 10 minutes
    importing on an HDD, and each node keeps about 7 GB for it.
  - The CPU limit (4) caps the latency, at about 2.5 s per post.
- **Verified:**
  - **`make start`** took about 12 minutes:
    - copying the 3.5 GB tarball to k3d's volume, 1 minute;
    - importing it into the three nodes in parallel, 9 minutes (00:43:12 →
      00:52:16);
    - the Helm releases and the LLM becoming ready, 1 minute.

    k3d deleted its copy of the tarball afterwards. Each node's containerd
    grew to about 8.5 GB, also on nodes that do not run the LLM, because
    the import unpacks the image everywhere.
  - **The pod:**
    - it loaded the model in 39 s, and the startup probe saw 503 while it
      loaded;
    - 3.5 GiB of memory, including the model's memory-mapped pages;
    - the Service's only endpoint is the real pod;
    - 0 image pulls.
  - **Checks:** `verify-boundary` 31/31, and `make llm-smoke` 3/3 (6.6 s for
    the first request, then about 2.5 s).

### D24. The summary worker (step 8)

- **Decision:**
  - **A CronJob `worker` in `analysis`**, as A8 planned, with the same
    settings as the ingestors (D19): `Forbid`, `startingDeadlineSeconds`
    120, `backoffLimit` 0, the shared hardening, and the `db-analysis`
    Secret mounted as a file.
    - **Schedule `2-59/5 * * * *`** (the author chose 5 minutes): it runs
      at :02, :07, :12…, two minutes after the ingestors, which take about
      10 s. Each run finds the posts they just stored.
    - **The pod carries `component: worker`**, so the existing `worker`
      NetworkPolicy lets it reach only PostgreSQL, the LLM and the DNS.
  - **One run** (`services/worker`):
    1. **Checks the LLM first.** If `/health` is not 200, for example while
       the model loads after a start, it touches nothing and exits 1. The
       model's name comes from `/v1/models` and is stored with every label.
    2. **Takes the subscriptions** whose summary is oldest first, and
       those without a summary before any other.
    3. **Classifies each post of the window only once** (A2, A9): the last
       50 posts of the last 7 days that have no label yet. Each label is
       stored as soon as it arrives, so a run cut short keeps its work.
    4. **Summarises only a fully classified window.** It counts the labels
       and picks the dominant one: the maximum, and `neutral` on any tie
       (A3). A summary of half the posts is never shown.
    5. **Rewrites the summary only if its posts changed**, and only then
       asks the LLM for the sentence. The posts changed if one was
       classified after the summary was written, or if the counts moved
       because a post left the window. `updated_at` is then the database's
       `now()`.
  - **The sentence:**
    - the prompt holds the 20 most recent posts, each cut to 280
      characters, on one line;
    - it also holds the counts and the dominant label, so the sentence
      cannot contradict the label shown next to it;
    - at most 30 words, in English, temperature 0, `max_tokens` 100;
    - the posts are declared as data, not instructions.
  - **A time budget per run:**
    - no new LLM call starts after 180 s, and the longest call is the
      sentence, with a 90 s timeout, so the worst case is about 270 s;
    - the Job's `activeDeadlineSeconds` (285 s) is only a safety net,
      below the 300 s between runs;
    - the chart refuses to render if the budget plus the sentence timeout
      reach the deadline;
    - whatever is left is picked up by the next run, 5 minutes later.
  - **Failures:**

    | What fails | What happens |
    |---|---|
    | The LLM is not ready at the start | Nothing is touched; exit 1 |
    | The LLM stops answering, returns 503 or takes more than 30 s for a label | The run stops; the labels already stored are kept; exit 1 |
    | An unusable label, or a database error, for one subscription | That subscription is skipped; the others go on; exit 1 |
    | The sentence fails or times out | The summary is stored with its label and counts and no sentence (degraded mode, A3); the next run retries the sentence |
    | The budget runs out before the sentence | The same: fresh counts now, the sentence next run |
    | The subscription is deleted during the run | Nothing stored; not a failure |

  - **The evaluation reuses the worker's client.** `tools/llm_eval.py` now
    imports `socialsignal_worker.llm` and runs in the worker image, so it
    measures exactly the prompts the worker sends.
- **Alternatives:**
  - **Classify inside the ingestor**, which the author asked about. It
    would let the internet-facing zone reach the LLM, which the boundary
    forbids and `verify-boundary` checks. It would also need more grants
    for `ingestor`, and it would tie ingestion to the LLM: while the LLM is
    down or slow, ingestion would stop or run past its deadline. A9 already
    ruled it out.
  - **The ingestor notifies the worker when it finishes:**
    - by creating a Job through the Kubernetes API: that gives the
      internet-facing zone rights over `analysis`, and `ingest` cannot
      reach the Kubernetes API anyway;
    - through PostgreSQL `NOTIFY`/`LISTEN`, crossing zones only through
      `data`: it keeps the boundary, but needs an always-running worker,
      reconnection handling and a periodic sweep for missed notifications,
      to save a few minutes at most. It is an open item.
  - **A Deployment with an internal loop.** Rejected in A8: it needs its
    own guard against overlapping runs, and it holds resources between
    runs.
  - **Every 10 or 15 minutes.** Running less often saves no LLM work, since
    each post is classified once; it only delays the summary. An idle run
    costs a few seconds of a small pod.
  - **Rewrite `updated_at` on every run**, meaning "checked as of". Rejected
    by the author: `updated_at` is when the summary was generated.
  - **Keep the previous sentence when a new one fails.** It would describe
    other posts than the counts next to it.
  - **A `mixed` label for ties.** It needs a schema change, and the counts
    already show the split.
- **Why:**
  - Classification stays in the analysis zone.
  - The cost of the LLM is bounded by new posts, not by the schedule.
  - Nothing is lost when a run is cut short: labels are kept, and the
    summary is only written from complete data.
  - Every failure is visible as a failed Job, while the analysts keep
    seeing the last summary with its date.
- **Trade-off:**
  - **Freshness:** at most about 7 minutes from a handle's ingestion to
    its summary, about 25 for a hashtag.
  - **`updated_at` does not tell "no new posts" from "the worker is not
    running":** a quiet handle shows an old date even when everything
    works. A failed Job shows the second case.
  - **One change is not detected:** a post classified earlier for another
    subscription that replaces a post with the same label in a full window
    of 50. The counts are still right; only the sentence could describe a
    slightly older set.
  - **A post the LLM could never label** would fail its subscription on
    every run. With the label constrained by a JSON schema, and posts of at
    most 300 characters in an 8192-token context, no such case is known.
  - **A timed-out request may keep the LLM's only slot busy** until the
    server finishes it, so the next call can time out too. The run then
    stops, and the next run continues.
  - **After `make start`,** the first run can find the LLM still loading:
    that Job fails, and the next one does the work.
- **Verified:**
  - **Before deploying:**
    - 43 new unit tests, 96 in total, with fakes of the database and the

    - the image: 50 MB, uid 10001, no source code, imports and settings

  - **The stored model name** is `gemma-4-E2B-it-qat-q4_0`, from

  - **The sentences** (temperature 0):
    - `@bsky.app`: "The subscription has a positive sentiment, focusing on

  - **Recovery (00:02 run):** with no manual step, it classified the 3 new

  - **A run with nothing new** (the README's manual run): both
    subscriptions `unchanged`, no LLM call, `updated_at` untouched.

### D25. The API and the minimal UI (step 9)

The author accepted every recommendation, and asked that what already
worked stay untouched.

- **Decision:**
  - **FastAPI, served by uvicorn**, in `services/api`, as a Deployment
    `api` in `analysis` with 2 replicas, behind Traefik on
    `http://localhost:8088` (D3).
  - **A page rendered on the server with Jinja2**, with no JavaScript and
    no external assets:
    - a form to subscribe, with the kind and the value;
    - a table with, for each subscription: the dominant label, a bar and
      the count per label, the number of posts, the LLM's sentence, and
      when the summary was updated (relative, with the UTC time on hover);
    - an "Unsubscribe" button per row;
    - after a successful form post, a 303 redirect to the page
      (post/redirect/get), so reloading never posts again.
  - **Every state is explained:**

    | State | When | The page says |
    |---|---|---|
    | pending | no post was ever stored for it | waiting for the first posts; check the account or tag exists if it lasts |
    | analysing | posts stored, no summary yet | being analysed |
    | empty | summary of 0 posts | no posts in the last 7 days |
    | ready | summary of 1 or more posts | label, counts, posts, sentence, time |

    A ready summary without a sentence says so (degraded mode, A3).
  - **A small JSON API** with the same code:
    - `GET /api/subscriptions`;
    - `POST /api/subscriptions`: 201 if created, 200 if it already existed;
    - `DELETE /api/subscriptions/{id}`: 204, or 404.
  - **`/docs` and `/redoc` are disabled:** Swagger UI loads its JavaScript
    from a CDN, which an isolated network cannot reach.
  - **Probes:** `/healthz` (liveness) and `/readyz` (readiness) check only
    the process, not the database.
  - **Validation, without internet access:**
    - handles follow the AT Protocol's syntax; hashtags have no spaces and
      at most 64 characters and 640 bytes;
    - both are stored without `@` or `#` and in lower case, as the ingestor
      expects;
    - the API cannot ask Bluesky whether an account exists, so a typo stays
      "pending".
  - **Writes from another origin are refused (403).** For POST, PUT, PATCH
    and DELETE, an `Origin` header must match the `Host`. Clients without
    `Origin`, like curl, are allowed.
  - **One database connection per request,** through the shared
    `connect()`, as the `analysis` role. A database error becomes a page,
    or a JSON answer, saying that the database is not reachable, with a 503.
  - **The pod:** the chart's shared hardening, a writable `/tmp` (an
    `emptyDir` of 16 MiB) for form parsing, and the worker's window values,
    so the page states what "recent" means.
- **Alternatives:**
  - **A single-page app with JavaScript.** More code, a build step, and
    nothing the brief needs.
  - **Readiness that checks the database.** With PostgreSQL down, every
    replica would turn unready at once: Traefik would answer a bare 503,
    and Kubernetes would gain nothing, since no replica could serve anyway.
  - **A connection pool (`psycopg-pool`),** first in the plan. It saves a
    few milliseconds per request, but adds failure modes: connections that
    died while PostgreSQL restarted, or a pool that gave up reconnecting.
    Fine for an analysts' UI; an open item if traffic grows.
  - **Validating handles against Bluesky.** Impossible from the analysis
    zone without breaking the boundary. The ingestor could record why a
    subscription has no posts; it is an open item.
  - **A CSRF token in each form.** Stronger, but needs a session or a
    secret. The `Origin` check covers browsers, which are the threat with
    no login.
- **Why:**
  - Server-rendered HTML with autoescaping is the smallest UI that meets
    the brief, and it works offline.
  - The sentence is written from posts off the internet, and the template
    escapes it.
  - The API only reads what the worker precomputed, so it keeps answering
    while the LLM is down.
- **Trade-off:**
  - The page does not refresh itself; the analyst reloads it.
  - Anyone on the analysts' network can change the subscriptions (A4).
  - A non-existent account and one not fetched yet look the same:
    "pending".
  - Changing `uv.lock` gives every Python image a new tag (D15), although
    the other services' content is the same (checked).
- **Verified:**
  - **Before deploying:**
    - 52 new unit tests, 148 in total: validation, every state, an
      escaped `<script>`, a cross-site post refused, a database outage, and
      probes that keep answering;
    - the image: uid 10001, the template inside the package, imports
      working with `--network none`;
    - `migrations`, `ingestor` and `worker` got new tags because the lock
      changed. Their packages, versions and code are identical to the
      previous images: the same hash of the `dist-info` list and of every
      `socialsignal` source file;
    - the rendered release against the deployed one: apart from the new
      Deployment, Service and Ingress, only those image tags differ.
  - **In the cluster:**
    - 2 replicas ready on different nodes; `GET /` through Traefik 200 in
      0.4 s, then about 20 ms;
    - from another pod, `api.analysis.svc:8000` is refused (curl exit 7);
      through Traefik, 200;
    - **end to end:** `@AtProto.com` subscribed through the form (303)
      was stored as `atproto.com` and shown as pending. The next ingestor
      stored 48 posts, and the page said "being analysed". Three minutes
      later the worker summarised its 3 recent posts (`neutral`, with a
      sentence), visible on the page and in the API;
    - a cross-site form post got 403, `two words` as a hashtag 400 with
      the reason, and `#Python` again 200 with the existing id;
    - **unsubscribing through the form** got 303, and a second `DELETE`
      404. The cascade removed the link and the summary; the 48 posts and
      their 3 labels stayed;
    - **PostgreSQL scaled to 0:** the page answered 503 in 10 ms with "The
      database is not reachable right now", the JSON API 503, and both
      pods stayed `Ready`. Once PostgreSQL was back, the API answered 200
      within seconds, without restarting.
  - **What must stay untouched, checked:**
    - the NetworkPolicies, the database chart, the migration and the
      platform manifests have the same checksums;
    - no change under the other services, the shared package, the scripts
      or the other templates;
    - the LLM image is the same (`dec1162d9ccc`), and `.env` was not
      touched;
    - `make verify-boundary` 31/31, and `make llm-smoke` 3/3.

### D26. High availability and updates without downtime (step 10)

The author asked to go ahead with step 10. The agent stated the plan
before starting and changed it twice when measurements disproved it, as
recorded below.

- **Decision:**
  - **The API:**
    - **rolling update:** `maxSurge: 1`, `maxUnavailable: 0`,
      `minReadySeconds: 5`;
    - **spread:** a topology spread constraint over
      `kubernetes.io/hostname`, `maxSkew: 1`, `DoNotSchedule`, with
      `nodeTaintsPolicy: Honor`, so a cordoned node is not counted and the
      evicted pod can still be placed;
    - **PodDisruptionBudget** `minAvailable: 1` (a value, with 2 replicas);
    - **graceful shutdown:** a `preStop` `sleep` action of 10 s (no binary
      needed), then uvicorn's `timeout_graceful_shutdown` of 15 s;
      `terminationGracePeriodSeconds: 30`;
    - **DNS:** `dnsConfig` options `timeout:1` and `attempts:3`.
  - **The platform on the analysts' path** (`deploy/platform/20-high-availability.yaml`):
    - **Traefik:** a `HelmChartConfig`, k3s' supported way to override its
      bundled chart, with 2 replicas, a PDB (`minAvailable: 1`), the same
      spread constraint and a `preStop` of 10 s. k3s' Helm controller
      applies it with a Job, from the chart k3s serves itself.
    - **CoreDNS:** a PDB (`minAvailable: 1`), and `make start` scales it to
      2. k3s owns that Deployment, but its manifest leaves the replica
      count out, so k3s does not reset it; k3s' own spread constraint
      places the two pods on different nodes.
  - **Repeatable demos** (`scripts/ha-demo.sh`):
    - `make demo-update` restarts the API's Deployment, the same rolling
      update a new image triggers;
    - `make demo-drain` drains a node that runs an API pod, never
      PostgreSQL's, then uncordons it, also on failure or interruption;
    - both send requests to the JSON API through Traefik from the host
      several times per second, keep the load on until the old pods are
      gone, print the failures per second, and exit 1 if any request
      failed.
- **What the measurements changed:**
  1. **Two replicas everywhere were not enough.** The first drain, of a
     node running an API, a Traefik and a CoreDNS pod, failed 86 of 356
     requests.
  2. **Ruled out, one test each, with probes on every node's port 80:**
     cordoning alone (0 of 767 failed), creating and deleting a pod in
     `ingest` (0 of 676), and deleting a finished Job's pod (0 of 367).
     Draining a node without Traefik or CoreDNS: 0 failed.
  3. **Found:** the failures started 1-2 s after the drain began, as
     instant refusals on every node, `/readyz` included. `kubectl drain`
     prints "evicted" when a pod is gone, not when its eviction starts, and
     the Traefik and CoreDNS pods had started stopping just before the
     failures. Traefik closes its listener on SIGTERM while kube-proxy
     still sends it connections. **Fix:** Traefik's `preStop`. Next drain:
     1 failure in 206.
  4. **The last failure:** a request sent at the moment the CoreDNS pod
     stopped (k3s' Corefile has no `lameduck`) timed out after 5 s, the
     resolver's default before retrying. **Fix:** the API's 1 s DNS
     timeout. Next drains: 0 failures.
  5. **The demo itself was wrong at first:** it stopped the load as soon
     as the rollout reported success, while an old pod was still in its
     10 s pause, exactly when failures would happen. It now waits until
     the old pods are gone.
- **Alternatives:**
  - **Traefik as a DaemonSet,** one per node. More pods than needed on a
    larger cluster; two replicas and a PDB are enough.
  - **Traefik's `requestAcceptGraceTimeout`** instead of a `preStop`. Same
    effect inside Traefik; the `preStop` is the same mechanism as the API's,
    so there is one idea to explain.
  - **Patching CoreDNS** with a `preStop`, or editing its Corefile. k3s
    owns both and says not to edit them; the retry is in our own chart.
    NodeLocal DNSCache is the on-prem answer (open item).
  - **A readiness endpoint that turns 503 on SIGTERM** instead of a pause.
    The endpoint is removed from the Service as soon as the pod starts
    terminating anyway; what is missing is time for every node and
    Traefik to notice, which only a pause gives.
  - **Pod anti-affinity** instead of a spread constraint. The same result
    for one pod per node; the spread constraint also handles more replicas
    than nodes.
  - **Drain any node, PostgreSQL's included.** That is an outage of about
    6 s by design until CloudNativePG (D14), so the demo avoids it and says
    so.
- **Why:** the brief asks for high availability for the analysts. The
  measurements showed it depends on the whole path, not only on our
  replicas.
- **Trade-off:**
  - Every API and Traefik pod takes 10 s longer to stop.
  - CoreDNS's count is set imperatively by `make start`; k3s has no
    declarative setting for it.
  - A drain or an update stops running CronJob pods: that Job fails, and
    the next run catches up.
  - Each drain moves pods around; Kubernetes does not move them back after
    an uncordon.
  - Once, before Traefik's pause was added, a burst of 502s followed an
    uncordon for 3 s. It did not appear again in five later drains and
    rollouts, and it is not explained.
- **Verified:**
  - **Platform:** 2 CoreDNS and 2 Traefik pods on different nodes, and 3
    PDBs (API, Traefik, CoreDNS), each allowing 1 disruption. Applying the
    `HelmChartConfig` updated Traefik under load without a failed request.
  - **Rolling updates:**
    - the first, real `make start` of this step, with old pods that did
      not have the pause yet: 1 of 1332 requests got a 502, when the last
      old pod stopped;
    - `make demo-update`: 359 of 359;
    - a later `make start` with a new pod template: 901 of 901.
  - **Drains:**
    - a node with only an API pod: 190 of 190;
    - the node with an API, a Traefik and a CoreDNS pod and the LLM: 237
      of 237 in 36 s. The LLM moved and was ready again for
      `make llm-smoke`.
  - **Afterwards:** `make verify-boundary` 31/31, `make llm-smoke` 3/3.
    The two worker runs stopped by drains ended `Failed`, and the next run
    summarised `#python` again.

## 4. Repository layout (step 2)

### R1. Project name

- **Decision:** `socialsignal`, used for the Python packages
  (`socialsignal-*`), the Helm chart and the cluster.

### R2. uv workspace with one member per deployable

- **Decision:** a **virtual** workspace root (a `pyproject.toml` with no
  `[project]` table) and these members, all sharing one `uv.lock`:
  - `packages/common`: shared settings and database access.
  - `services/ingestor`, `services/worker`, `services/api`: one per
    deployable.

  Members use the `src/` layout and the `uv_build` backend
  (`uv_build>=0.12.21,<0.13.0`, the constraint generated by
  `uv init --package` with uv 0.12.21).
- **Alternatives:**
  - one package with several entry points (simpler, but every image carries
    every dependency);
  - independent projects with separate lock files (versions can drift
    between services).
- **Why:** each image installs only its own member and dependencies
  (`uv sync --frozen --package <member>`), which gives smaller images and a
  smaller attack surface (the ingestor never carries the web stack). One lock
  file keeps shared dependencies on the same versions.
- **Trade-off:** a shared lock means one service cannot upgrade a shared
  dependency alone. Four `pyproject.toml` files to maintain. Where the
  migrations live is decided in step 4.

### R3. Makefile placeholders fail loudly

- **Decision:** targets that are not implemented yet print the step that
  will implement them and their recipe exits with status 1, so `make` itself
  fails (GNU make reports a failed target with exit status 2).
- **Alternatives:** empty targets that succeed.
- **Why:** a placeholder can never be mistaken for a working build.
- **Trade-off:** none worth noting while the targets are being filled in.
  Since step 3c every target is implemented and the placeholder helper has
  been removed.

### R4. AI traceability is versioned

- **Decision:** `BRIEF.md`, `CLAUDE.md` (the AI agent's instructions) and
  [`AI_USAGE.md`](AI_USAGE.md) (a per-step log of AI use) are part of the
  repository.
- **Alternatives:** describe AI use only in a short section of `DESIGN.md`.
- **Why:** the brief encourages AI agents and asks the author to be able to
  defend the result; keeping the prompts, the rules and the log in the repo
  makes the process auditable.
- **Trade-off:** it exposes internal working notes to the reviewer.
